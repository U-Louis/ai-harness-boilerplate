# What an AI coding-agent harness is

Source dossier. Research date: 27 October 2026. Read against sections 1 and 4 of `ai-harness-state-of-the-art.md`. That file was not edited.

Pages below were fetched in full unless a claim is marked as a snippet. “Primary” means the author or organization did the work, or published the definition on their own site or as a preprint. A later retelling is labeled second-hand.

## 1. What the harness is

A coding-agent harness is the software around a model that lets the model act: the loop, the tools, the rules for what enters each context window, the safety controls, the orchestration, and the places where hooks and skills attach. That is the definition that stabilized in early 2026 (LangChain’s Vivek Trivedy, 10 March 2026; Claude Code’s own docs; Barbaste et al., July 2026). Prompt engineering is the writing of instructions. Context engineering is the ongoing choice of which tokens reach each model call, and those tokens include tool descriptions, retrieved files, state, and history, not only the user’s sentence (Anthropic Applied AI, 29 September 2025; Karpathy, 25 June 2025). The harness is the machine that performs that curation and also executes actions and decides when to stop. A second, narrower use is the outer harness a team builds around a coding agent that already has a loop: guides before the agent acts, and sensors after, some of them ordinary programs and some of them another model (Böckeler, 2 April 2026; Hashimoto, 5 February 2026; the repository practice in Lopopolo, 11 February 2026). The dry run is that outer policy. It becomes a harness only when a runtime executes it.

## 2. Ranked sources

Ranked by how directly they fix the definition, then by how much shipped practice they add. Dates are the dates printed on the pages.

### 1. Vivek Trivedy, LangChain, “The Anatomy of an Agent Harness,” 10 March 2026

https://www.langchain.com/blog/the-anatomy-of-an-agent-harness

Why it is primary: LangChain builds agent libraries and the Deep Agents harness. This is the post that put `agent = model + harness` into circulation as an explicit definition. The later source-code study (source 10) credits it as the popularizer of that formula.

Concrete claims:

- If it is not the model, it is the harness: system prompts, tools, skills, MCP servers and their descriptions, filesystem, sandbox, browser, orchestration (subagents, handoffs, model routing), and hooks or middleware for deterministic steps such as compaction, continuation, and lint checks.
- A raw model emits text. Durable state, code execution, live knowledge, and environment setup are harness features. A chat product is already a harness: a loop that stores messages.
- The filesystem is the foundational primitive: a workspace, an offload for context, a record that outlives a session, and a shared surface for humans and agents. Git is the versioning layer on that surface.
- Bash plus code execution is the general-purpose tool, so the harness does not have to pre-build every action. Other tools still ship. Sandboxes, allow-lists, and network isolation are how that execution stays bounded. Browsers, logs, screenshots, and test runners are how the agent checks its own work.
- Context rot is why the harness compacts, offloads large tool results to the filesystem, and loads skills by progressive disclosure instead of dumping every tool into the window at start. Trivedy writes that harnesses are “largely delivery mechanisms for good context engineering.”
- Long runs add file-backed state, a Ralph loop (a hook that rejects an early exit and restarts the original goal in a fresh window), planning files, and verification hooks that re-run a test suite and return the error. Models are post-trained inside particular harnesses, so a model can do worse in the harness it was trained with than in another. He cites Terminal-Bench 2.0, where Opus 4.6 in Claude Code scored below the same model in other harnesses, and a LangChain coding agent that moved from roughly top 30 to top 5 on that board by changing the harness only. Those leaderboard claims are his report of public boards and a previous LangChain post; this dossier did not re-score them.

### 2. Ryan Lopopolo, OpenAI, “Harness engineering: leveraging Codex in an agent-first world,” 11 February 2026

https://openai.com/index/harness-engineering/

Why it is primary: a first-person account of one team shipping an internal product with Codex. Zach Brock and Victor Zhu are acknowledged as contributors. This is the case study the dry run leans on. It does not contain the prompt / context / harness lifetime table.

Concrete claims:

- From late August 2025 to the post, about five months, three engineers and later seven drove Codex to on the order of a million lines and about 1,500 merged pull requests, averaging 3.5 pull requests per engineer per day, with throughput rising as the team grew. The product had hundreds of internal users and external alpha testers. They estimate about one tenth the time of writing it by hand. Humans wrote none of the code, including CI, docs, observability, and the initial scaffold (repository structure, CI, formatting, package manager, application framework, and the first `AGENTS.md`), which Codex CLI generated from templates with GPT-5.
- The human job became environment design, intent, and feedback loops. When something failed, the question was which capability was missing and how to make it legible and enforceable. “Try harder” was almost never the fix. Humans steer through prompts. Agents open the pull requests, review them, and often squash-merge them. Humans may review and are not required to. The team pushed review toward agent-to-agent. They name that review-until-satisfied loop a Ralph Wiggum loop.
- Repository knowledge is the system of record. A giant `AGENTS.md` failed because it crowded out the task, made every rule equally “important,” rotted, and could not be checked. The replacement is a map of about 100 lines plus a versioned `docs/` tree (design docs, execution plans, product specs, quality, reliability, security). Linters and CI check freshness and cross-links. A doc-gardening agent opens fix-up pull requests. Anything the agent cannot read in the repo, including Slack and people’s heads, effectively does not exist.
- Invariants are mechanical; local implementation is free. Custom linters enforce layer dependency direction, structured logging, naming, file size, and reliability rules, and the error text tells the agent how to comply. Data is parsed at boundaries; the library is not prescribed. Agents copy existing patterns, including bad ones, so “golden principles” are encoded and background tasks open small refactoring pull requests. The team had been spending Fridays, about 20 percent of the week, cleaning this up by hand.
- Application legibility is a prerequisite for numeric budgets. Per-worktree boot, Chrome DevTools Protocol, DOM snapshots, screenshots, and an ephemeral logs/metrics/traces stack made prompts such as “startup under 800 ms” and “no span in these four critical journeys exceeds two seconds” tractable. Single runs of six hours were regular. Minimal blocking merge gates and short-lived pull requests were a throughput choice they say would be irresponsible at low throughput. End-to-end autonomy “depends heavily on the specific structure and tooling of this repository and should not be assumed to generalize without similar investment—at least, not yet.”
- They use “scaffold” for that initial repository skeleton, and “harness engineering” as the name of the human practice. They never define harness as a layer whose lifetime is “the whole build,” distinct from a one-turn prompt and a one-session context.

### 3. Anthropic Applied AI (Prithvi Rajasekaran, Ethan Dixon, Carly Ryan, Jeremy Hadfield), “Effective context engineering for AI agents,” 29 September 2025

https://www.anthropic.com/engineering/effective-context-engineering-for-ai-agents

Why it is primary: Anthropic’s own distinction between prompt engineering and context engineering, written from Claude Code and customer work. This is the page to cite for that split. It does not use the word harness for a third lifetime.

Concrete claims:

- Prompt engineering is writing and organizing instructions, especially system prompts, and was the main craft when most jobs were one-shot. Context engineering is curating the whole token state at inference time: system instructions, tools, MCP, external data, and message history. It is iterative. The curation happens every time something is passed to the model.
- Context rots. As the window grows, recall and long-range reasoning get worse, as a gradient, because attention is finite. The working rule is the smallest set of high-signal tokens that still produces the desired behavior. System prompts should sit between brittle if-else logic and vague slogans.
- Bloated or overlapping tool sets are a common failure. If a human cannot say which tool applies, the agent will not do better. Tools should return token-efficient results. Few-shot examples should be a small canonical set, not a laundry list of edge cases.
- Just-in-time retrieval beats stuffing the window. Claude Code keeps `CLAUDE.md` in context up front and uses glob, grep, and bash (`head`, `tail`) to load the rest. Folder names and timestamps are themselves signals. Exploration is slower than precomputed retrieval and needs heuristics or the agent wastes the window.
- For work that exceeds one window they name three context-engineering techniques, not a separate discipline: compaction (summarize and restart; Claude Code keeps the summary plus the five most recently touched files; tool-result clearing is the lightest form), structured notes outside the window (`NOTES.md`, to-do lists, a file-backed memory tool), and sub-agents that return a 1,000–2,000 token summary after spending tens of thousands of tokens. They point their multi-agent evidence at a research system, not at a coding swarm. Compaction can drop details whose importance shows up later.

Companion primary, same organization, 11 September 2025: Ken Aizawa, “Writing effective tools for agents — with agents,” https://www.anthropic.com/engineering/writing-tools-for-agents. Tools are a contract with a non-deterministic caller, so they should not be thin wrappers of every API. Build a few high-impact tools, consolidate chained calls, namespace them, paginate or truncate (Claude Code caps tool responses at 25,000 tokens by default), and make errors say how to fix the call. Their Slack example cut a tool response from 206 tokens to 72. Small edits to tool descriptions moved Claude Sonnet 3.5 to a then state-of-the-art SWE-bench Verified score. That last figure is Anthropic’s claim about their own eval; this dossier did not re-run it.

### 4. Birgitta Böckeler, Thoughtworks, “Harness engineering for coding agent users,” Martin Fowler, 2 April 2026

https://www.martinfowler.com/articles/harness-engineering.html

Why it is primary: a practitioner essay that narrows the wide definition for people using coding agents, and that states the relationship to context engineering in one sentence. It supersedes her 17 February 2026 memo. She discloses that Claude was used to gather notes and polish language. She cites OpenAI and Stripe as examples; those two were re-read here as their own pages (sources 2 and 6).

Concrete claims:

- `Agent = model + harness` is too wide to use without a bounded context. Coding products already contain an inner harness (system prompt, retrieval, orchestration). Users then build an outer harness for one codebase. She keeps the awkward “harness around a harness” because the two jobs differ.
- Guides are feedforward: they steer before the agent acts (`AGENTS.md`, skills, codemods, bootstrap scripts). Sensors are feedback: they observe after and should speak in a form the model can use, such as a linter message that includes the repair. Either one alone fails. Guides without sensors never learn whether the rule worked. Sensors without guides repeat the same mistake.
- Computational controls (tests, linters, type checks, structural tests such as ArchUnit) are deterministic and cheap enough to run on every change. Inferential controls (semantic review, an LLM judge) are slower and non-deterministic. They can raise trust when the model fits the task. They do not become reliable because they are called a gate.
- “Engineering a user harness for a coding agent is a specific form of context engineering.” Context engineering is how guides and sensors reach the agent. That sentence nests the dry run’s three rows.
- The human steering loop is: a repeated failure becomes a better guide or sensor, and agents can write those controls. Checks should sit as far left as their cost allows. Some sensors watch drift continuously, outside the change lifecycle (dead code, coverage quality, SLO decay).
- She splits what is being regulated. Maintainability is the easy harness, because linters already exist. Architecture fitness is requirements plus tests for properties such as performance and logging. Behaviour is unsolved: a spec plus a green AI-written test suite still puts too much faith in the tests. Approved fixtures help in some areas only. Misdiagnosis, extra features, and misunderstood instructions are not reliably caught by either kind of sensor. If the human never specified the behavior, no sensor has a target. A good outer harness directs human attention. It is an ongoing practice, and she asks how to detect a sensor that never fires because it cannot see, rather than because the code is clean.

### 5. Justin Young, Anthropic, “Effective harnesses for long-running agents,” 26 November 2025

https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents

Why it is primary: Anthropic engineering, with a published quickstart, on making the Claude Agent SDK survive many fresh context windows. The dry run’s session pattern comes from here. The page uses “harness” at two sizes, which matters.

Concrete claims:

- The Claude Agent SDK is “a powerful, general-purpose agent harness”: tools, planning, execution, and compaction. Compaction alone did not get Opus 4.5 to a production-quality app from a high-level prompt such as “build a clone of claude.ai.”
- Two failures: the agent one-shots the app and dies mid-feature, and a later session sees partial work and declares victory. The response is an initializer session and then one feature per later session, ending in a state fit to merge: no major bugs, orderly, documented.
- Footnote: initializer and coding agent are separate only because the user prompt differs. System prompt, tools, and harness are the same.
- The initializer writes `init.sh`, a progress log, an initial git commit, and a JSON feature list. Features start failing. JSON was chosen because the model was less likely to overwrite it than Markdown. Coding agents are prompted to change only the `passes` field, with strong wording against deleting or editing tests. The coding agent itself marks a feature passing, and only after it has tested.
- Each coding session starts with `pwd`, the git log, the progress file, and the feature list, boots the app, and checks a core journey before new work. It ends with a commit and a progress note. Git is how a bad change is reverted.
- Unit tests and `curl` still left features broken. End-to-end browser automation (Puppeteer MCP) fixed many of those. Native alert dialogs were invisible to that tool, and features that depended on them stayed buggier. The post leaves open whether one general agent or specialists (test, QA, cleanup) would do better, and says the demo is tuned for full-stack web apps.

### 6. Stripe, “Minions: Stripe’s one-shot, end-to-end coding agents,” parts 1 and 2

https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents

https://stripe.dev/blog/minions-stripes-one-shot-end-to-end-coding-agents-part-2

Why it is primary: Stripe describing the unattended coding agents they run on their own codebase. The fetched pages show no byline and no publication date. Part 2 presents itself as the later account (about 1,300 merged minion pull requests per week, up from about 1,000 in part 1). Böckeler’s April 2026 article already treats the write-up as public, so the posts are not later than that.

Concrete claims:

- A minion run starts from Slack or an internal tool and ends at a branch that has passed CI, with no human in between. Merged minion pull requests are human-reviewed and contain no human-written code. Part 1 says the engineer opens the pull request and asks another engineer to review, or sends the minion back with more instructions. The harness is a fork of Block’s goose, customized for unattended runs. Cursor and Claude Code cover the supervised case. Because there is no one looking over its shoulder, the harness cannot depend on interruptibility.
- They call the orchestrator a blueprint: a code state machine whose nodes are either deterministic (run the configured linters, push) or an agent loop (implement the task, fix CI). Anticipatable steps stay in code so the model is not spending tokens on them. Agent nodes still get wide latitude. “Putting LLMs into contained boxes” is their reliability claim. The same blueprint machinery constrains a subagent’s tools, system prompt, or conversation.
- Safety is the environment, not a confirmation prompt. Minions run with full permissions inside a pre-warmed devbox in QA: no production data, no production services, no arbitrary network egress. Mistakes are confined to one box. Isolation is why they skip per-action approval.
- Tool registry: an internal MCP server, Toolshed, held more than 400 tools in part 1 and nearly 500 in part 2. Agents do better in a “smaller box,” so each agent, including minions, receives a curated subset, with optional thematic add-ons. A separate security-control framework blocks destructive tool use. That is a registry plus an allow-list, not “one bash tool” and not “every API as a tool.”
- Rules are path-scoped. Unconditional global rules would fill the window before work starts. They standardized on Cursor’s rule format and sync it so minions, Cursor, and Claude Code read the same files.
- Feedback is shifted left and then capped. A lint subset runs as a deterministic node before push, using a daemon that usually returns in well under a second (part 1 says the local lint executable takes less than five seconds). CI is entered once. Autofixes apply automatically. Failures without an autofix go back to an agent node for one local repair and a second push. After that second CI run the branch returns to the human. They refuse an unbounded CI loop because tokens, compute, and time have diminishing returns. The suite they are not running locally is more than three million tests.

### 7. Mitchell Hashimoto, “My AI Adoption Journey,” 5 February 2026

https://mitchellh.com/writing/my-ai-adoption-journey

Why it is primary: the earliest clear use of “harness engineering” found in this pass, six days before OpenAI’s post, by someone shipping Ghostty and with no stated AI-vendor role. He says the post is hand-written. The dry run’s own source list already marked this post as second-hand via Augment. The URL is public. Augment’s guide said it could not be recovered (see section 6).

Concrete claims:

- He uses the phrase because he does not know a settled industry term, and he will drop it if a better one exists. His meaning is narrow: every time an agent makes a mistake, engineer so that mistake cannot recur.
- Two mechanisms only. Implicit prompting: one line in `AGENTS.md` per observed bad behavior. He says Ghostty’s file almost completely removed the behaviors it names (wrong commands, wrong APIs). Programmed tools: screenshot scripts, filtered test runners, and an `AGENTS.md` line that tells the agent they exist. The point of the tools is fast, high-quality evidence that the agent is wrong, or that it is right.
- An agent, for him, is a model that can chat and call out in a loop. The minimum loop is read files, execute programs, and make HTTP requests. Chatbots fail on brownfield work because the human becomes the copy-paste harness.
- Practices he arrived at before naming the harness: one actionable task per session, a separate planning session when the request is vague, and a verification path so the agent fixes itself. He does not describe role separation, merge policy, or a product-spec pipeline.
- At the time of writing he wanted one background agent, not a swarm, and estimated he actually had one running 10 to 20 percent of a working day. He would not let triage agents post public replies.

### 8. Anthropic, Claude Code docs, “How Claude Code works”

https://code.claude.com/docs/en/how-claude-code-works

Why it is primary: the product document for a coding agent that Anthropic ships. Fetched 27 October 2026. The page is undated living documentation, so it describes the product as of that fetch, not a single historical release.

Concrete claims:

- “The agentic loop is powered by two components: models that reason and tools that act. Claude Code is the layer around the model that provides the tools and manages the context the model sees. This surrounding layer is what the term agentic harness refers to.”
- The loop’s three phases — gather context, take action, verify — blend. The model decides the next phase from the previous tool result. The human can interrupt or queue a correction inside the same turn. Built-in tools cover files, search, shell, web, and optional code intelligence. Skills, MCP, hooks, and subagents sit on top of that loop.
- A new session starts with a fresh window. What persists is files, git, `CLAUDE.md` or `AGENTS.md`, auto-memory (the first 200 lines or 25 KB of `MEMORY.md`), and skills loaded on demand. Compaction summarizes when the window fills and can drop early instructions, so durable rules go in `CLAUDE.md`. MCP tool definitions stay deferred until tool search loads one. Subagents run in their own window and return a summary.
- Safety on this page is permissions plus checkpoints, not a process gate on the product spec. Checkpoints snapshot files before edits and are separate from git; they do not cover databases, APIs, or deploys. Permission modes as fetched: Auto (a classifier blocks risky actions), Manual (ask before edits and shell), Accept edits (filesystem edits without asking, other commands still ask), and Plan (explore, do not edit source). Organization settings can allow-list commands such as `npm test`.
- The same loop runs locally, in Anthropic-managed or self-hosted cloud VMs, or via Remote Control, where the UI is remote and the files stay local. The execution environment changes. The harness description does not.

### 9. Linyue Pan, Lexiao Zou, Shuo Guo, Jingchen Ni, Hai-Tao Zheng, “Natural-Language Agent Harnesses,” arXiv:2603.25723, submitted 26 March 2026

https://arxiv.org/abs/2603.25723

https://arxiv.org/html/2603.25723

Why it is primary: a real preprint (Tsinghua Shenzhen; corresponding author Hai-Tao Zheng). The abs record says “under review.” Claims below are from the HTML full text fetched 27 October 2026, whose abstract wording is slightly fuller than the abs blurb. It is one model (`gpt-5.4-mini`), one Codex CLI build (0.123.0), and three benchmark families. It is not a production postmortem. It is the clearest experiment on the gap between a policy document and a runtime.

Concrete claims:

- A harness is the external system that decides what the model sees, which tools it may call, where state lives, how observations return, when validation runs, how failure is recovered, when to stop, and how calls are organized. Harness engineering is designing, debugging, and evaluating that system.
- They split policy from mechanism. A natural-language agent harness (NLAH) states stages, roles, state rules, evidence, retry, and stop conditions. A shared runtime (IHR) turns those clauses into child-agent calls, files, and hooks. Tests, parsers, sandboxing, and artifact validators stay in code. Phrases such as “be careful” are weak policy. “Write a state file before delegating” is executable policy.
- Three realizations of the same idea, primary metric in percent: Live-SWE code 67.0, the same text as an ordinary prompt 77.0, IHR-executed NLAH 73.0. Terminal-Bench 2.0 / MHTBA: 36.0, 57.3, 53.9. OSWorld / SeeAct: 47.1, 47.9, 46.3. Prompt-only text matched or beat the runtime interpreter. The readable policy shrank sharply (Live-SWE from 60.1k tokens of code materials to a 2.9k-token NLAH). Their appendix says the MHTBA code score is depressed by a stopping bug: of 89 samples, 66 hit `AgentTimeoutError`, and 21 of those already had verifier reward 1.0. The “natural language beat the code harness” result on that benchmark is partly a broken controller, not a pure win for prose.
- Module ablations under one runtime: file-backed state helped both reported settings (SWE 73.0 to 75.6, OSWorld 44.4 to 58.3). An explicit verifier helped OSWorld by 8.4 points and SWE by 0.2. Context compression hurt both (SWE 73.0 to 72.0, OSWorld 44.4 to 36.1). Multi-candidate search raised agent calls and dropped SWE from 73.0 to 71.4. The modules that helped made the path to the evaluator’s acceptance condition shorter. Extra process did not.
- For production they keep safety, permissions, evaluation, and parsing in code. A portable natural-language harness is also an attack surface (prompt injection, tool grafting, supply-chain contamination) and wants provenance, review, permissions, and a sandbox.

### 10. Paul Barbaste, Tristan Darrigol, Germain Vu, Tom Wiltberger, “Harness Engineering: Anatomy, Architecture, and Evolution of Coding Agents,” arXiv:2609.00006, submitted 15 July 2026

https://arxiv.org/abs/2609.00006

Why it is primary: a source-code anatomy of eleven coding-agent codebases plus a meta-harness, from Inclusive Brains and Wavestone AI Lab. It is a preprint, not a peer-reviewed journal article. Claude Code is analyzed from a circulated source snapshot, not from an official public repository. Section 3.7’s market news is explicitly not source-verified; those corporate claims are left out of this dossier. Self-reported SWE-bench numbers for the 100-line baseline carry the authors’ own caveat. What is usable is the boundary-setting in section 2 and the subsystem map tied to named code.

Concrete claims:

- Working definition, which they adopt from Trivedy and from an operational definition by Macedo: an agent is a model plus a harness, and the harness is the runtime that couples the model to the world through a loop, tools, context, safety, orchestration, and extension surfaces. Harness engineering is the design and evolution of that runtime.
- Near-synonyms they want kept apart. Scaffold: the structural code (loop, registries). Mini-SWE-Agent’s scaffold is about 100 lines; Claude Code’s harness is a product with a UI, permissions, and plugins. Framework: a library you import (LangChain, AutoGen, CrewAI). Harness: a runtime you work inside. They say that 2025 distinction was already dissolving in 2026, from both directions. Evaluation harness: wraps an agent to score it. Agent harness: wraps a model so it can act. Orchestrator or meta-harness: coordinates harnesses and has no editing loop of its own. They treat Databricks’ Omnigent that way.
- Every system in the corpus takes a position on seven subsystems: agent loop, model integration, tools, memory and context, safety and permissions, orchestration, extensibility. The floor is a while-loop, one template, one bash tool, a message list, and two limits. The ceiling they observed for safety is Codex: policy rules, an LLM approval reviewer, and an OS sandbox on three platforms (Bubblewrap on Linux, Seatbelt on macOS, restricted tokens on Windows), with protected paths such as `.git` kept read-only. Claude Code’s OS sandbox is opt-in via Anthropic’s sandbox-runtime. OpenCode’s “sandbox” in tree is worktrees plus permission rules, not an OS sandbox. Pi ships no sandbox by default, on purpose, and documents extensions.
- Two absences across the eleven, in their count roughly four million lines: none import a general-purpose agent framework, and none retrieve code with vector embeddings. Retrieval is ripgrep, tree-sitter, glob, and Markdown files discovered on disk. Skills (`SKILL.md`) were in 9 of 11; MCP in 8 of 11.
- Prompt text is not a mechanism. OpenCode’s edit-tool description says the tool will error if you edit a file you have not read; they found no read-tracking in the tool source. Hermes is the system that actually vetoes a final answer when code changed and no fresh verification exists (verify-on-stop). Across all eleven prompts they found operational guardrails (destructive git, secrets, dangerous shell) and no duplicate of the model provider’s misuse policy. From their April to July snapshots, behavioral policy was moving out of prompt prose and into configuration, and Codex had copied Claude Code’s hook vocabulary.

### 11. Walden Yan, Cognition, two posts on context and writers

https://cognition.com/blog/dont-build-multi-agents (12 June 2025)

https://cognition.com/blog/multi-agents-working (22 April 2026)

Why they are primary: Cognition ships Devin. The second post is an explicit revision of the first, from production use, not a recap of OpenAI or Anthropic. Figures are vendor-reported.

Concrete claims from June 2025:

- Context engineering is the reliability problem for long-running agents, and he defines it as doing dynamically what prompt engineering did by hand for a chatbot. It is “the #1 job of engineers building AI agents.”
- Share full traces, not a rewritten subtask. Actions carry implicit decisions (style, edge cases). Parallel writers therefore diverge. His default is one linear agent. A compressor model can extend the trace, and he says Cognition has fine-tuned one; getting the summary right is the hard part.
- As of that date, Claude Code’s subagents did not write code in parallel with the parent. They answered questions so the parent’s window stayed smaller. He treats OpenAI Swarm and AutoGen’s multi-agent defaults as the wrong push for production reliability in 2025.

Concrete claims from April 2026:

- The ban on parallel writers still stands. What they now deploy is extra agents that contribute intelligence while one agent writes.
- Devin Review, on pull requests Devin itself wrote, catches on average 2 bugs per pull request, about 58 percent of them severe (logic, missing edge cases, security). It works best when the reviewer does not share the coder’s context. The reasons he gives are context rot and attention, plus the reviewer having to reconstruct intent from the diff, including cases where the user asked for an insecure pattern. The writer must still filter those findings against the original instructions, or the loop expands scope.
- A “smart friend” tool, a stronger model called by a weaker one, did not pay off while the primary was too weak to know when to ask (their SWE-1.5 result). It did pay off between two frontier models used as a capability router. A manager agent that spawns children is live in Devin and mostly fails at communication: children do not share state just because the manager assumes they do, and discoveries do not propagate unless that path is built. Unstructured swarms are, in his words, mostly a distraction. Large public demos with a simple verifiable success criterion (a browser, a compiler) are a different problem from software whose quality is taste.

### 12. Andrej Karpathy, two posts on X

Context engineering, 25 June 2025: https://x.com/karpathy/status/1937902205765607626

Agentic engineering, about 4 February 2026: https://x.com/karpathy/status/2019137879310836075

A later February 2026 post, https://x.com/karpathy/status/2026731645169185220, uses the same phrase for orchestrators with tools, memory, and instructions.

Why they are primary: Karpathy’s own posts. They are included because they are the usual citations for “context engineering” and “agentic engineering,” and because neither post defines a harness. The full text was read through a public mirror (`xitter.cf`) and matches contemporaneous reprints (a June 2025 archive of the first post, and February 2026 press for the second). `x.com` itself was not the fetch that returned the body. He is agreeing with “context engineering,” a phrasing already in use; contemporaneous archives attribute the 18 June 2025 push for that phrase to Tobi Lütke. Lütke’s post was not fetched in this pass.

Concrete claims:

- People hear “prompt” as a short task blurb. In an industrial LLM app, context engineering is filling the window with the right information for the next step: task text, explanations, few-shot examples, retrieval, possibly multimodal data, tools, state, history, and compacting. Too little, or the wrong shape, and the model lacks what it needs. Too much, or irrelevant, and cost goes up and performance goes down.
- Context engineering sits inside a thicker layer he does not name: control flow, packing each window, routing to models of different capability, generation-and-verification UI, guardrails, security, evaluations, parallelism, and prefetching. That unnamed layer is the closest he comes to what Trivedy later calls a harness. He does not use the word.
- In the February 2026 post, “agentic engineering” is the human practice that replaces vibe coding for professional work. Agentic: you are not writing the code directly about 99 percent of the time; you orchestrate agents and act as oversight. Engineering: there is a learnable art and science to doing that without giving up software quality. It is not a component diagram.
- The later February post adds that the pattern works better when the task is well specified and the result can be verified, and that it still needs direction, judgment, taste, and iteration. His home-lab anecdote (a video dashboard finished in about 30 minutes with no edits from him) is one report, not a measured result.

### Other primaries consulted, not given a full rank entry

These were fetched or checked far enough to use. They do not change the definition above. They fill tool design, the pre-2026 vocabulary, and one deletion experiment.

- Anthropic, “Building effective agents,” 19 December 2024, https://www.anthropic.com/engineering/building-effective-agents. Confirmed from the official page’s opening and summary as returned in search, not from a full re-read of the article. The page itself now says the December 2024 tooling landscape has changed and points readers at Claude Managed Agents. What still matters as lineage: the successful customer systems were simple composable patterns; workflows are predefined code paths and agents are model-directed loops; start with prompts and evals and add an agent only when the simpler thing fails; spend as much care on the agent-computer interface as on a human interface, including tool formats the model has already seen in text. Stripe’s blueprint is this workflow-plus-agent split, implemented. SWE-agent’s ACI is the academic ancestor of that third principle.
- John Yang and colleagues, “SWE-agent: Agent-Computer Interfaces Enable Automated Software Engineering,” arXiv:2405.15793, May 2024, https://arxiv.org/abs/2405.15793. Abstract only in this pass, plus the project’s ACI note at https://github.com/princeton-nlp/SWE-agent/blob/main/docs/background/aci.md as indexed in search. The paper’s claim is that a purpose-built interface (how the model views, edits, searches, and runs a repo) changes SWE-bench results, reported there as 12.5 percent pass@1. The project note lists four interface choices: a linter that blocks a syntactically invalid edit, a 100-line file viewer, a search command that lists matching files rather than dumping context, and an explicit message when a command prints nothing. That is harness design under an older name. The paper body was not re-read here, so the 12.5 percent figure is the abstract’s, not a number re-derived from the tables.
- Andrew Qu, Vercel, “We removed 80% of our agent’s tools,” 22 December 2025, https://vercel.com/blog/we-removed-80-percent-of-our-agents-tools. Primary for one internal text-to-SQL agent (d0). They deleted specialized tools, prompt scaffolding, and hand-built retrieval, and left the model bash over the semantic-layer files inside a Vercel Sandbox. On five representative queries the file-system version beat the previous one: mean 274.8 s to 77.4 s, about 102k tokens to about 61k, about 12 steps to about 7, and 4/5 success to 5/5. The worst old run failed after 724 seconds, 100 steps, and 145,463 tokens; the new agent finished that query in 141 seconds, 19 steps, and 67,483 tokens. Five queries, one internal agent. A companion post, Ashka Stephen, 9 January 2026, https://vercel.com/blog/how-to-build-agents-with-filesystems-and-bash, generalizes the pattern and separates “trust the reasoning” from “the sandbox limits the action.” This disagrees with “build many thoughtful tools” only when the specialized tool was summarizing a corpus the model can already read. Stripe’s Toolshed result is the other side: networked internal systems still need a curated registry.

## 3. Conflicts between sources

**What the word covers.** Trivedy, the Claude Code docs, and Barbaste et al. put the loop, tools, prompts, and sandbox inside the harness. Hashimoto uses the same phrase for a habit: encode each new mistake as an `AGENTS.md` line or a script. Lopopolo uses it for the human practice of environments, intent, and feedback loops, and uses “scaffold” for the generated repository skeleton. Böckeler accepts the wide formula and then splits inner product harness from outer user harness. Pan et al. split again, along policy versus mechanism: the natural-language document is the harness policy, and the runtime is what makes a gate real. LangChain’s own docs, https://docs.langchain.com/oss/python/concepts/products, fetched 27 October 2026 and undated, use a third cut: a runtime is a durable-execution engine (LangGraph, Temporal), a framework is the library (LangChain, Vercel AI SDK, OpenAI Agents SDK), and a harness is the opinionated battery-included layer (Deep Agents, and they list the Claude Agent SDK and Manus beside it). That page and Trivedy’s post are the same company. A later LangChain post, Sydney Runkle, “How to Build a Custom Agent Harness,” 3 June 2026, https://www.langchain.com/blog/how-to-build-a-custom-agent-harness, says the harness is the scaffolding that connects the model to the world and that its job is to give the model the right context at every step. That job description was taken from the post’s key takeaways in search; the full post was not re-fetched. It pulls the harness back toward context delivery, which is narrower than Trivedy’s March list.

**Where context engineering sits.** Anthropic (September 2025) treats context engineering as the successor craft to prompt engineering, repeated at every model call, and uses it to cover compaction, notes, and sub-agents across many hours. Karpathy puts tools, state, history, and compacting inside context engineering, and puts control flow, guardrails, security, and evals in a thicker layer above it. Böckeler says the outer coding harness is a form of context engineering, with computational sensors added beside the tokens. Yan (June 2025) says context engineering is the main job of agent builders and barely uses “harness.” Trivedy says harnesses exist largely to deliver context engineering, and also to execute and constrain. Augment’s lifetime table (one turn, one window, whole task) matches none of these. See section 6.

**Scaffold.** Lopopolo: the initial repo, CI, and framework. Barbaste et al.: the loop and the registries, as distinct from the shipped product that embeds them. Anthropic’s December 2024 post and the SWE-agent paper use agent-computer interface for the tool-and-format surface Barbaste would file under tools. The three uses can be told apart only by naming the author.

**How deterministic a gate is.** Lopopolo’s mature repository has few blocking merge gates, because waiting was more expensive than a follow-up fix, and he limits that advice to a repository that already had months of tooling. Stripe keeps lint and push deterministic, leaves implementation and CI repair to an agent node, and stops after two CI rounds, returning the branch to a human. Young’s feature gates are prompts: the model is told not to edit tests and told to flip `passes` only after browser testing. There is no separate permission principal. Pan et al. found that the same policy, pasted as an ordinary prompt, scored as high or higher than a runtime built to enforce it, and they still insist that validators and sandboxes stay in code. Böckeler says computational sensors catch structure and do not catch “you misunderstood the task.” Hermes, in Barbaste’s reading, is one of the few codebases that turns “don’t stop without fresh verification” into an actual veto rather than a sentence in the prompt. Claude Code’s current docs add a different enforcement layer again: a permission classifier and checkpoints, which are neither a product-spec gate nor a CI job.

**How many agents, and who writes.** Young leaves specialists as an open question and, in the demo, uses one harness with two prompts. Yan in 2025 argues against parallel writers. Yan in 2026 ships a clean-context reviewer and a manager, and still wants a single writer. His reason for a fresh reviewer is context rot, which means “same model, opposing goal” is the wrong mechanism story: the gain he reports comes from a short window and a diff read without the coder’s trace, and the coder must still reconcile findings with the user’s instructions. Anthropic’s September 2025 post cites a research multi-agent system as a context-management win (parallel exploration, summarized back). That is a different task from editing one codebase. Lopopolo runs many Codex sessions, including agent reviewers, and lets the implementing agent merge. Those reviewers are not described as a frozen read-only role with a different tool allow-list.

**How many tools.** Aizawa: a few thoughtful tools, consolidation, token-cheap responses, errors that teach. Qu: on one internal analyst agent, deleting the specialized tools and leaving bash over readable files won on five queries. Trivedy: ship bash as the general tool, and still ship browsers, logs, and test runners. Stripe: hundreds of MCP tools exist centrally, and each agent is handed a small subset, because a smaller box worked better, while bash cannot see their internal SaaS. Lopopolo added specialized Chrome DevTools and PromQL skills once the app and its telemetry were actually legible to the agent. The consistent rule is narrower than “fewer tools”: do not build a tool that only retells something the model can already open, and do build a tool when the system is otherwise invisible or unsafe.

**What “runtime” means.** LangChain docs: durable execution under the agent. Pan et al.: the interpreter of harness policy. Barbaste et al.: the harness is the runtime. Claude Code docs: local machine, cloud VM, or remote-controlled local machine, with the same loop. Stripe: a QA devbox that already existed for humans. Using one of these as a synonym for the others will smuggle in the wrong layer.

**Whether the document is the system.** The dry run opens with “This file is the harness.” Pan et al. are the direct evidence against that sentence. A document can be the policy. Their prompt-only condition is a document. Their scores say a document can steer a run that already has a loop, a terminal, and a sandbox. Their production note says the document does not replace those. Böckeler’s outer harness is the same distinction from the user’s side: the file you write assumes Claude Code, Codex, or an equivalent inner harness.

## 4. What the dry run already got right

Section 1 is careful about OpenAI’s end state, and that caution matches the post. Lopopolo’s numbers (about a million lines, about 1,500 pull requests, agent-to-agent review, few blocking merge gates, months of repository-specific tooling, do not assume it generalizes) are in the post. So is the decision not to start by letting the builder merge its own work. Young really does leave one general agent versus specialists unresolved. Keeping one model and several fresh contexts is compatible with his footnote that the two “agents” shared a harness.

The repository practice in sections 1 and 4 tracks Lopopolo closely, and the later artifact layout in the dry run follows his published tree more tightly than a paraphrase would: short map, deep docs, execution plans, product specs, a quality grade, reliability, security, progressive disclosure, doc gardening, mechanical checks whose errors teach the repair, strict boundaries with local freedom inside them, and background cleanup because agents copy bad local patterns. “Humans steer; agents execute” and “when it fails, add a capability or an enforceable rule” are his sentences in substance. Human time as the scarce resource is his framing too.

Principles 2, 3, 4, 7, 9, and 10 have primary homes even where the dry run’s citation is Augment or left implicit:

- Durable files, not the previous chat, are Young’s whole point, and Anthropic’s September 2025 note-taking section, and Trivedy’s filesystem primitive.
- A short map plus on-demand depth is Lopopolo’s table-of-contents `AGENTS.md` and Anthropic’s just-in-time retrieval. Stripe’s path-scoped rules are the same idea at larger scale.
- Invariants over local style are Lopopolo’s layer rules and taste invariants.
- Evidence as command, version, and result, rather than a summary, is in the spirit of Lopopolo’s legibility requirement and of Pan et al.’s “name the artifact.” The dry run is stricter than either about who may record a pass. That stricter rule is discussed in section 5.
- Small, bootable, revertible slices are Young’s clean end-of-session state plus git as the recovery tool. Lopopolo’s per-worktree boot is the same recoverability at a higher throughput.
- A repeated review comment promoted into a doc and then a check is Hashimoto’s mistake-to-rule habit, Lopopolo’s “promote the rule into code,” and Böckeler’s steering loop. The dry run’s section 18 already says the Hashimoto attribution was second-hand. The practice is still his, and the URL is source 7.

The session ritual the dry run takes from Young is accurate where it stays with him: one feature at a time, a feature list that starts failing, JSON so the model is less tempted to rewrite it, a prompt not to delete tests, `init.sh`, a progress log, read history before new work, boot and re-check the core journey, commit at the end. The warning that browser automation misses some UI (he names native alerts) is in the post, and the dry run’s later note about recording blind spots follows it. End-to-end driving of the product, rather than unit tests or a `curl`, is his result.

Principle 6, many readers and one writer, matches Yan’s April 2026 conclusion, including the value of a reviewer who did not watch the implementation. The dry run cites other articles for that pattern. The shipped-system source is Cognition. Principle 1, one prompt with one purpose, is a reasonable reading of Young’s two user prompts and of Hashimoto’s “don’t draw the owl in one session.” It is not how Claude Code’s product loop is documented: gather, act, and verify blend inside one session.

Section 2’s split between “taken from published practice” and “inferred” is the right kind of hygiene. Several inferences are now easier to hang on a primary without promoting them to facts: start with invariants and legibility before self-merge (Lopopolo says the low-friction merge is a late property of one repository); cap retries (Stripe’s two CI rounds); spend human attention on intent and on the diff classes that sensors miss (Böckeler’s behaviour harness, and her point that misunderstood instructions survive both linters and LLM judges).

## 5. What it missed, overclaimed, or should cite differently

**The lifetime table is the main correction.** Section 1 says prompt, context, and harness are three disciplines with lifetimes of one turn, one session, and the whole build, and it sources that split to Lopopolo and to Augment. Lopopolo does not draw it. Augment does, and Augment is a vendor synthesis with attribution errors (section 6). The primaries nest the terms. Anthropic: context engineering replaced prompt engineering as the name of the craft and runs at every inference, including across many hours, via compaction and notes. Karpathy: tools and state are inside context engineering; guardrails and evals sit in a thicker layer he does not call a harness. Böckeler: the outer harness a coding-agent user builds is a form of context engineering. Trivedy: the harness includes the system prompt and exists in large part to do context engineering, and it also executes tools and enforces constraints. A citation that keeps the table should point at Augment only, and should say the table conflicts with Anthropic, Karpathy, Böckeler, and Trivedy.

**“This file is the harness” overclaims.** The dry run is outer policy: roles, artifact schemas, and intended gates. Böckeler’s name for that is the outer harness, and it assumes an inner one (the product’s loop, tools, and permissions). Pan et al.’s name is harness policy, and their experiment says the prose does not, by itself, implement validation, sandboxing, or stopping. Claude Code’s docs locate the harness in tools, context management, and the execution environment. The dry run should be cited as a specification of an outer harness. The executing harness is whatever runs those prompts, mounts the tools, and fails the checks.

**The Anthropic feature-list rule is tightened past the source.** Young tells the coding agent to change only `passes`, and the coding agent self-verifies. The dry run’s section 2 still says “the agent” flips the flag after end-to-end verification, which matches him. The `features.json` section says only the verifier sets `passes`, and labels the block “source: Anthropic.” That writer restriction is the dry run’s own control. It is a plausible response to his “don’t let it rewrite the tests” prompt, and to Yan’s clean-context reviewer, and it is not what Anthropic shipped in the write-up. Pan et al.’s verifier module gained 8.4 points on OSWorld and 0.2 on SWE under their setup, so a separate checker is not a uniform win; it helped when its judgment matched the evaluator’s. Yan’s 2 bugs per pull request, 58 percent severe, is Devin Review on Devin’s pull requests, and he still requires the writer to filter the reviewer’s findings. “Same model, opposing goal, fresh session” is the dry run’s inference. The mechanism the shipped review post actually argues is a short context and no shared trace.

**Phase gates are cited to the wrong grade of source.** “Plan, then execute, then verify, and a gate at each boundary beats a test after generation” is attributed to Augment’s PEV pattern and listed under published practice next to OpenAI and Anthropic. Young’s actual comparison is end-to-end browser testing versus unit tests and `curl`, inside one coding session. Claude Code’s docs describe gather, act, and verify as blended, model-chosen, and interruptible. Lopopolo’s outer loop is “review until the agent reviewers are satisfied,” followed by a merge philosophy with few blocking gates. Stripe is the primary that actually publishes a phase machine, and it is mixed: deterministic nodes only where the step is anticipatable, agent nodes for implementation and CI repair, and a hard stop after two CI rounds rather than a gate on every transition. Böckeler distributes checks by cost (shift left) and keeps a class of failures outside every sensor. NLAH-style stage names are useful as policy and, on their numbers, do not outrun the same text used as a prompt. Principle 5, “anything that must always be true is a check the runtime can fail,” should be narrowed to what a program can observe. Behaviour against an unstated intent is the gap Böckeler names, and it is the gap a green suite does not close.

**Tool boundaries and safety are a different layer from role permissions.** The dry run’s tool boundary is mostly which role may write product code, tests, or an approval. Shipped harnesses also have an execution safety layer the dry run does not specify: Claude Code’s permission modes and file checkpoints; Codex’s OS sandbox plus an approval reviewer, as Barbaste et al. read the code; Stripe’s QA devbox with no production data and no arbitrary egress, which is why they allow full permissions and skip confirmations. Those are not interchangeable. A human gate on auth diffs does not sandbox a shell, and a sandbox does not decide whether the product intent was right. Tool-registry design is also missing. The primaries to add are Aizawa (few tools, token-cheap results, errors that teach), Qu (deleting tools that only summarized readable files, five-query caveat), Stripe’s Toolshed (a large central registry, a small per-agent subset, a security framework on top), and Trivedy and Lopopolo on bash, browsers, and observability once the system is legible. SWE-agent’s ACI is the 2024 ancestor: the shape of the edit and search interface changed outcomes before “harness” was the word.

**Context is not “one session,” and notes are not all equal.** Anthropic’s context-engineering post and Claude Code’s docs put compaction and tool-result eviction inside a single session, because the window fills before the session ends. The dry run’s “durable artifacts, not chat memory” matches their note-taking advice and Young’s progress file. Pan et al. then split the carriers: file-backed state helped on both benchmarks they ablated; context compression hurt both; free-form markdown memory helped one and hurt the other. A `progress.md` that a later session treats as truth can drop the detail the next decision needs. The dry run already wants required fields and recorded dead ends. The citation for “dead ends matter” should stay concrete: Young’s progress file is so the next session does not guess, and Pan et al.’s compression result is the warning that a summary is a lossy sensor.

**Inner harness versus outer harness is the missing sentence in section 1.** The design principles are outer-harness principles. They assume some product already supplies the loop, the shell, compaction, and a permission model. Hashimoto’s two forms (a line in `AGENTS.md`, a script the agent can run) are the smallest outer harness, not the Claude Code architecture. Karpathy’s “agentic engineering” is the human oversight practice, not a synonym for either layer. Citing him for the harness will import the wrong object.

**OpenAI’s scaffold and the academic scaffold.** Where the dry run follows Lopopolo’s repository story it can keep his word: the scaffold is the generated skeleton of the repo. Where it means the agent loop, Barbaste et al. and the SWE-agent line are the sources, and they mean something else.

**What section 20 should stop carrying as equal sources.** Augment is the provenance of the lifetime table, the PEV gate claim, the “constraints, then feedback, then gates” order, and the second-hand Hashimoto, Apiiro, and SWE-bench mentions. Those should be re-cited to sources 2, 4, 5, 6, and 7, or marked as Augment’s framing. RayLabs, QualityLayer, developertoolkit.ai, Wavect, and Quash were not re-fetched for this dossier. The dry run uses them for independent review, human gates, and the ways green tests hide authorization and query bugs. Yan (April 2026) and Böckeler (behaviour harness; AI-written tests) now cover those points as stronger primaries. GitLab’s checkpoint page was not re-fetched either; Böckeler and Stripe are the better citations for “shift the human to intent and to what sensors cannot see,” and Lopopolo is the citation for human time as the scarce resource.
